# AI-Ready 通用项目管理规范｜精简执行版
> **版本：v1.4 Final｜定位：强制规则的唯一正式来源**  
> 本文件由 zedboot skill 分发，对应源规范 v1.4。
> 适用于网站、App、游戏、AI、数据、自动化、研究、课程、商业与设计项目。

# 0. AI 快速指令块
1. **MUST** 先读 `AGENTS.md`，再按其中顺序读 README、规则、索引、状态和 TODO。
2. **MUST NOT** 在索引有效时无目的扫描整个项目、归档、依赖或构建目录。
3. **MUST** 先识别项目模式、框架和现有结构，再决定目录；不得机械套用模板。
4. **MUST** 先确认任务、验收标准、当前写入者、Git 状态和未提交修改，再写文件。
5. **MUST** 同一时间只有一个当前写入者；其他 AI 只能分析或审查。
6. **MUST NOT** 在 `main` 上开发未完成的代码任务。
7. **MUST** 在任务、状态、重要文件或重大决议变化时同步对应文档。
8. **MUST** 在新增、删除、移动或重命名重要文件时更新索引。
9. **MUST** 在任务收尾时检查：新增文件已归位且命名规范、根目录无临时或错位文件、被替代的旧文件已删除或归档。
10. **MUST** 在首次接手或长期中断后恢复时，先向用户输出“项目识别摘要”，确认理解后再实施。
11. **MUST** 只把任务推进到“待验收”；用户是默认且唯一最终验收人。
12. **MUST** 在暂停、切换 AI 或上下文不足前至少更新 `PROJECT_STATE.md`。
13. **MUST NOT** 提交密钥、密码、`.env`、真实隐私数据或不应入库的大文件。
14. **MUST** 向无法浏览目录的 AI 提供标准交接包。
15. **SHOULD** 优先复用合理现有结构；分类收益不明显时不增加目录。
16. **SHOULD** 让项目文件中的状态始终比聊天记录更可靠。

# 1. 规则等级与角色
- **MUST / MUST NOT**：强制。
- **SHOULD / SHOULD NOT**：默认执行；偏离时说明理由。
- **MAY**：可选。
- **用户**：项目负责人、决策人和最终验收人。
- **AI**：参与分析、执行或审查的模型。
- **当前写入者**：当前唯一获准修改文件的用户或 AI。
- **审查 AI**：只读、分析和建议，不直接写入。
统一使用“AI”这一术语。

# 2. 项目模式
初始化时 MUST 在 `PROJECT_INDEX.md` 标记模式。
| 模式 | Git | 完成条件 |
|---|---|---|
| 可部署代码项目 | MUST | 用户验收 + 正式部署/构建 + 文档与版本收尾 |
| 无部署交付项目 | SHOULD；用户可明确选择不使用 | 最终文件进入约定位置 + 用户验收 + 文档收尾 |
| 混合项目 | 代码部分 MUST | 每个任务注明代码发布、非代码交付或混合路径 |
无部署项目不要求虚构生产环境或 Git Tag。

# 3. 项目入口与正式来源
## 3.1 入口
- `README.md`：用户入口。
- `AGENTS.md`：AI 入口。
- `docs/README.md`：文档中心。
## 3.2 单一事实来源
| 信息 | 正式来源 |
|---|---|
| 项目简介 | `README.md` |
| AI 工作规则 | `AGENTS.md` + 本规范 |
| 文件地图 | `docs/project/PROJECT_INDEX.md` |
| 当前状态 | `docs/project/PROJECT_STATE.md` |
| 当前与未来任务 | `docs/project/TODO.md` |
| 重大决定 | `docs/project/DECISION_LOG.md` |
| 用户可见变化 | `CHANGELOG.md` |
| 正式版本/交付 | `docs/releases/vX.Y.Z.md` |
| 代码细节 | Git Commit |
| 历史文件 | `archive/README.md` |
同一份完整信息 MUST NOT 在多个文件中重复维护。README 只保留 3～4 个高频入口，其余指向索引。

# 4. 自适应目录规则
## 4.1 决策顺序
AI MUST 按以下顺序设计或调整目录：
1. 框架、平台、语言或游戏引擎强制结构；
2. 项目已有且合理的结构；
3. 独立运行、构建、部署或交付边界；
4. 业务功能边界；
5. 已发生的真实共享需求；
6. 文件数量与查找成本。
不得为了模板一致破坏框架，或无收益地大规模搬迁。
## 4.2 创建目录前
MUST 能回答：
- 它解决什么实际问题？
- 是否有稳定职责？
- 是否已有合适目录？
- 是否只有一个普通文件？
- 是否会长期增长？
- 分类收益是否高于维护成本？
默认规则：
- 同类文件达到两个以上，或已批准任务即将产生多个同类文件时，MAY 建立子目录。
- 单个普通文件 SHOULD 放入职责最接近的位置。
- 常用文件 SHOULD 尽量在根目录下 3～5 层内定位；框架强制层级除外。
- MUST NOT 创建大量空目录、重复路径或 `misc/`、`other/`、`final/`、`latest/` 等无稳定职责目录。
- 不确定时选择更简单的结构。
## 4.3 根目录
根目录只长期保留：`README.md`、`AGENTS.md`、`CHANGELOG.md`、`LICENSE`、`.gitignore` 和运行必需配置。部署必需文件（如 `Dockerfile`、`docker-compose.yml`、`docker-entrypoint.sh`）视为运行必需配置。
截图、设计、数据、PPT、PDF、旧文件、临时脚本和交付物 MUST 归入对应目录或删除。
以下目录均为可选，不得为套模板而全部创建：
`apps/ packages/ docs/ assets/ tests/ scripts/ ops/ deliverables/ archive/`

# 5. 通用命名
除框架要求外，文件和目录 SHOULD：
- 使用小写英文和英文短横线；
- 表达内容与职责；
- 必要时包含日期、任务号、平台或版本；
- 避免空格和含义不清的缩写。
推荐：`system-overview.md`、`homepage-mobile-v2.png`、`survey-cleaned-2026-08.csv`。
禁止长期使用：`final-2/`、`new/`、`latest/`、`misc/`、`other/`、`temp/`、`最终版2/`。
当前有效版本由索引、Git 和发布记录确认，不能只依赖文件名。

# 6. 索引、状态与任务
## 6.1 `PROJECT_INDEX.md`
MUST 登记：
- 核心需求、架构、配置和数据库文件；
- PPT、PDF、Word、Excel、重要数据；
- 关键图片与设计；
- 部署、安全和外部资源入口；
- 当前有效版本与替代关系；
- 容易误判的文件。
普通代码 MAY 按模块登记，不逐文件登记。
以下变化 MUST 更新索引：重要文件新增、删除、移动、重命名；用途、状态或有效版本变化；外部入口变化；归档。
## 6.2 `PROJECT_STATE.md`
应包含以下核心字段：
- 项目目标；
- 当前版本、阶段、分支和写入者；
- 当前主要任务；
- 已完成与未完成；
- 最近 3～5 项变化；
- 一个明确下一步；
- 阻塞与恢复条件；
- 已冻结的重要规则；
- 关键文件、交接说明和 `SYNC_PENDING`。
SHOULD 控制在 150～200 行，不写成工作日志。
## 6.3 TODO
任务编号：`项目代码-三位数字`，例如 `WEB-012`。
状态：`候选 → 已批准 → 进行中 → 待验收 → 已完成`；特殊状态为 `已阻塞 / 已取消`。
编号永久递增，不重复使用。
每个任务 MUST 至少包含：编号、状态、需求或问题、验收标准、目标版本或目标交付、涉及文件或模块。

## 6.4 需求进入规则
- 用户明确要求、范围清楚且风险较低：建立任务并进入“已批准”。
- 只是想法或远期设想：进入“候选”，不得打断当前主要任务。
- 影响产品规则、架构、数据、安全、收费或高成本方向：先进入“候选”，完成影响分析和必要决议，经用户确认后再进入“已批准”。
- 紧急线上故障：MAY 中断当前任务，但 MUST 建立独立紧急任务、记录中断点，并在修复后恢复原任务状态。

## 6.5 并行任务上限
个人项目默认：
- 主要“进行中”任务：最多 1 个；
- 紧急修复任务：最多 1 个；
- “待验收”任务：可以多个；
- 候选任务：不限制。
只有在独立分支、明确文件边界且用户同意时，才可偏离上述上限。

# 7. 任务执行与验收
## 7.1 接手识别摘要
首次接手项目、长期中断后恢复或用户要求重新确认理解时，AI MUST 在修改文件前向用户输出：
- 项目名称与模式；
- 当前版本和阶段；
- 当前主要任务及状态；
- 当前分支与写入者；
- 最近进展；
- 当前阻塞；
- 下一步；
- 预计涉及文件。

摘要用于让用户确认 AI 没有误解项目，不替代 `PROJECT_STATE.md`。

## 7.2 开始任务
AI MUST：
1. 确认任务已由用户批准；
2. 确认验收标准；
3. 检查 Git 与未提交修改；
4. 确认自己是当前写入者；
5. 创建任务分支，或记录无 Git 模式；
6. 更新 TODO 与 PROJECT_STATE；
7. 再开始修改。
## 7.3 进入待验收（任务收尾检查清单）
进入待验收前 MUST 逐项完成以下检查，不得只凭“代码写完”就推进状态：
- 实现需求并逐项检查验收标准；
- 运行适用测试、构建或内容检查；
- 检查主要设备、格式或交付环境；
- 检查敏感信息；
- 本次新增和修改的文件已归入正确目录，命名符合第 5 章规则；
- 根目录无本次产生的临时、错位或状态不明文件；
- 被本次工作替代的旧文件已删除或归档，并更新索引；
- 同步索引、状态和必要文档；
- 完成 AGENTS.md「每任务收尾自检」五维检查（安全红线 / 一致性冲突 / 失效残留 / 功能 / 同步完整），修复后复跑机械检查，交付附一行自检结论（细则见项目 AGENTS.md）。
## 7.4 已完成
AI MUST NOT 自行把任务从“待验收”改为“已完成”。
可部署代码项目经用户确认后，还需：正式部署/构建、目标环境检查、版本与文档收尾、Git Tag。
无部署交付项目经用户确认后，还需：最终文件进入 `deliverables/` 或约定位置、格式检查、状态与交付记录收尾；Git Commit/Tag 仅在采用 Git 时要求。

# 8. Git、分支、Commit 与版本
本章对可部署代码项目为 MUST；对无部署交付项目为 SHOULD，但用户可明确选择无 Git 模式。
- 长期分支默认：`main`
- 远程仓库：每项目一个独立私有远程仓库（如 GitHub Private 仓库），仅作备份与版本管理，不用于服务器部署。
- push 时机：本地 Commit 按任务正常进行；push 到远程仓库只与发布/交付绑定——用户确认部署上线（或正式交付）时随发布流程一并推送，开发期不要求每次提交都推送。
- 任务分支：`task/web-012-payment`
- 编号大小写为有意约定：分支名中任务编号用小写（`task/web-012-payment`），Commit 中任务编号用大写（`feat(WEB-012): ...`）。
- 紧急分支：`hotfix/web-031-login-error`
- Commit：`类型(任务编号): 中文修改说明`
- 类型：`feat fix docs refactor test style security chore`
规则：
- 一个 Commit 表达一件完整事情；
- 不写“修改”“更新”“完成”；
- 不提交敏感数据；
- 已发布 Commit 不随意重写；
- 发布 Commit：`chore(release): 发布 vX.Y.Z`。
版本使用 `v主版本.功能版本.修复版本`。无部署项目 MAY 使用版本标识交付批次，但不强制 Git Tag。

# 9. 决议
重大产品、架构、权限、数据、安全、收费、部署或高成本目录调整 MUST 写入决议日志。
编号：`DR-项目代码-YYYYMMDD-序号`，例如 `DR-WEB-20260801-001`。
旧决议不得删除；新决议应说明替代关系。

# 10. 多 AI 与人机协作
- 任一时间只有一个当前写入者。
- 其他 AI MAY 研究、审查或提出方案，但 MUST NOT 同时修改同一项目副本。
- 切换写入者前 MUST 更新状态、说明未提交内容并提供交接包。
- 一个 AI 出方案、另一个 AI 执行时，执行 AI 以项目文件和用户确认内容为准。
- 冲突或重大歧义交由用户决定。
- 自动测试、构建或其他 AI 审查通过，不能代替用户验收。

# 11. 无上下文 AI 交接包
## 11.1 最小交接包
1. `AGENTS.md`
2. `PROJECT_STATE.md`
3. 当前任务完整内容
4. 任务直接相关文件
5. 明确禁止事项
6. 期望输出格式
## 11.2 推荐增加
索引相关章节、需求文档、相关决议、当前分支与最近 Commit、测试证据、必须保持不变的文件。
## 11.3 指令模板
```markdown
你正在接手【项目名称】的【任务编号/名称】。
先阅读：AGENTS、PROJECT_STATE、当前任务和附件。
本次只处理：
- 
禁止：
- 修改未列出的模块
- 改变已确认规则
- 覆盖来源不明内容
- 自行标记已完成
完成后输出：本轮完成内容、未完成内容、修改文件、验证结果、风险、下一步。
```

# 12. 更新触发
“实时更新”指当前工作会话内完成，且不得晚于下一次 Commit、任务切换、暂停、合并或交接。
| 事件 | MUST 更新 |
|---|---|
| 新需求 | TODO |
| 任务开始、阻塞、恢复、待验收 | TODO + PROJECT_STATE |
| 当前任务、下一步或阶段变化 | PROJECT_STATE；必要时 README 摘要 |
| 重要文件或外部入口变化 | PROJECT_INDEX |
| 重大决定 | DECISION_LOG |
| 用户可见变化 | CHANGELOG |
| 正式发布或交付 | 状态、TODO、发布/交付说明及适用版本文件；含远程仓库 push 与 Git Tag（采用 Git 时） |
| 归档 | PROJECT_INDEX + archive/README |
| 暂停、切换 AI 或上下文不足 | PROJECT_STATE |
| 强制规范变化 | 精简执行版 + 参考版对应部分 |
普通函数、样式微调、缓存和构建产物变化不更新索引。
CHANGELOG 默认使用 `Added / Changed / Fixed / Removed / Security` 英文分类，以兼容 Keep a Changelog 和常见工具；具体内容使用中文。

# 13. 异常与上下文不足
如果 AI 无法完成全部同步，MUST 至少更新 `PROJECT_STATE.md`，说明：实际已完成、未完成、未同步文档、下一步、风险和未提交文件。
使用：
```markdown
## SYNC_PENDING
- 尚未同步：
- 原因：
- 下一步：
- 相关文件：
```
下一位 AI MUST 先处理 `SYNC_PENDING`，再继续新开发。工具失败、权限不足或验证未执行时，不得声称已通过。

# 14. 归档
被替代但仍需追溯的文件进入 `archive/`。
归档判断发生在每次任务收尾（第 7.3 节），MUST NOT 留待定期维护检查才处理。
归档 MUST：确认替代文件、更新索引、更新 `archive/README.md`、修复引用、避免状态不明重复版本。
缓存、构建产物、无价值临时文件和敏感内容应删除或忽略，不归档。

# 15. 项目健康检查
## 15.1 接手快速检查
- 当前任务与 TODO；
- 当前分支与未提交修改；
- 当前写入者；
- 索引关键路径；
- `SYNC_PENDING`；
- 来源不明文件；
- 根目录是否存在不应长期保留或状态不明的文件。
## 15.2 完整维护检查
在发布、正式交付、大型功能完成、长期中断后或文件明显增多时检查：
- 根目录；
- README、版本、CHANGELOG 与 Tag；
- 状态和 TODO；
- 索引与文档链接；
- 应归档旧文件；
- 空壳目录、单文件多层目录和过度分类；
- 敏感数据；
- 常用文件定位效率。
大量问题应建立独立“项目整理”任务，不在业务任务中顺便大规模重构。

# 16. 最小体系与闭环
最低建议：
```text
README.md
AGENTS.md
CHANGELOG.md
docs/
├── README.md
└── project/
    ├── PROJECT_RULES.md
    ├── PROJECT_INDEX.md
    ├── PROJECT_STATE.md
    ├── TODO.md
    └── DECISION_LOG.md
archive/
└── README.md
```
闭环：
`需求 → 任务 → 必要决议 → 用户批准 → 确认写入者 → 分支/无 Git 模式 → 实施与验证 → 同步文档 → 待验收 → 用户验收 → 发布或交付 → 收尾 → 已完成`
最终原则：
> 项目文件中的状态必须比聊天记录更可靠。  
> 固定的是管理原则，不是目录名称。  
> 分类服务于使用，复杂度必须匹配项目真实规模。
