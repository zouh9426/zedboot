# 1. 如何使用本规范

## 1.1 两层结构

本规范采用：

- **精简执行版**：包含所有 MUST、MUST NOT 和关键 SHOULD 规则；
- **完整参考版**：解释原因、提供模板、示例和特殊情况。

AI 日常工作通常只需要：

1. 项目自己的 `AGENTS.md`；
2. 精简执行版；
3. 当前项目索引、状态和 TODO；
4. 当前任务相关文件。

只有在以下场景中，才查阅本参考版：

- 初始化新项目；
- 设计或重构目录；
- 选择代码/非代码验收路径；
- 发布或正式交付；
- 多 AI 交接；
- 编写管理文件模板；
- 处理索引、归档或维护问题。

## 1.2 版本同步

两份规范应使用相同版本号。

规范版本历史的唯一正式来源是本文件的“规范版本历史”章节；精简执行版只标注当前生效版本。

修改强制规则时：

1. 先修改精简执行版；
2. 检查本参考版中的解释和模板；
3. 更新版本历史；
4. 更新项目 `AGENTS.md` 中引用版本；
5. 必要时为当前项目建立迁移任务。

# 2. 设计目标

体系同时面向用户和 AI。

## 2.1 用户需要

用户进入项目后应快速知道：

- 项目是什么；
- 当前版本；
- 当前阶段；
- 最近完成什么；
- 下一步是什么；
- 是否被阻塞；
- 主要文件在哪里；
- 怎样运行、查看或提交。

## 2.2 AI 需要

AI 接手后应快速知道：

- 工作规则；
- 当前任务；
- 验收标准；
- 当前写入者；
- 当前分支；
- 哪些文件有效；
- 哪些规则不能改变；
- 结束前同步什么。

## 2.3 维护目标

体系应：

- 信息职责清楚；
- 重复维护最少；
- 更新触发明确；
- 历史可以追溯；
- 目录可以演进；
- 小项目不被复杂流程拖累；
- 大项目可以逐步扩展。

# 3. 规则语言和角色

## 3.1 规则语言

- **MUST**：必须执行。
- **MUST NOT**：明确禁止。
- **SHOULD**：通常应执行，偏离时说明原因。
- **SHOULD NOT**：通常不应执行。
- **MAY**：可选。

## 3.2 角色定义

### 用户

- 项目负责人；
- 产品和范围决策人；
- 最终验收人；
- 决定哪些 AI 可以写入文件。

### AI

统一指参与项目的所有模型，不再混用“大模型”“执行者”“下一位模型”。

### 当前写入者

当前唯一可以修改项目文件的一方，可以是用户或 AI。

### 审查 AI

只读取、分析和提出建议，不写入当前项目文件。

# 4. 项目模式与完成路径

## 4.1 为什么要区分模式

旧版规范默认所有项目都有：

- Git；
- 生产环境；
- 正式部署；
- Git Tag。

这不适用于课程报告、PPT、研究、设计和商业方案。

因此初始化时需要标记项目模式。

## 4.2 模式 A：可部署代码项目

示例：

- 网站；
- 后端 API；
- App；
- 游戏；
- 桌面软件；
- 自动化服务。

建议状态字段：

```markdown
- 项目模式：可部署代码项目
- 正式环境：
- 正式构建：
- Git：启用
```

“完成”通常意味着：

- 用户验收；
- 生产部署或正式构建完成；
- 目标环境验证；
- 版本说明和 Tag 完成。

## 4.3 模式 B：无部署交付项目

示例：

- 课程 PPT；
- 研究报告；
- 商业计划；
- 市场分析；
- 设计方案；
- 最终 PDF；
- 数据分析交付物。

建议状态字段：

```markdown
- 项目模式：无部署交付项目
- 最终交付位置：deliverables/
- 提交格式：
- Git：可选
```

“完成”意味着：

- 最终文件生成；
- 文件名、格式、页数或提交要求检查通过；
- 文件进入约定交付位置；
- 用户验收；
- 状态和交付记录同步。

不存在生产部署或 Git Tag 时，不要求虚构这些步骤。

## 4.4 模式 C：混合项目

例如：

- 网站代码 + 项目报告；
- 游戏 Demo + 答辩 PPT；
- AI 工具 + 研究分析；
- App + 商店素材。

每个任务应标明：

```markdown
- 验收路径：代码发布 / 非代码交付 / 混合
```

# 5. 双入口与文档中心

## 5.1 `README.md`

README 面向用户，只保留：

- 项目简介；
- 当前版本与阶段；
- 当前主要任务或下一步；
- 3 至 4 个最高频入口；
- 运行、查看或提交方式。

README 不保存：

- 完整任务列表；
- 完整历史；
- 详细文件索引；
- 所有决议；
- 逐步进展。

### 推荐模板

```markdown
# 项目名称

一句话说明项目。

## 项目概览

- 项目模式：
- 目标用户：
- 当前正式版本或交付版本：
- 当前阶段：
- 当前主要任务：
- 当前阻塞：

## 当前进展

- 最近完成：
- 下一步：

## 高频入口

| 目的 | 文件 |
|---|---|
| 当前状态 | docs/project/PROJECT_STATE.md |
| 当前任务 | docs/project/TODO.md |

## 运行、查看或提交

填写本项目实际方式。
```

# 6. 单一事实来源

| 问题 | 正式来源 | 不应由谁重复承担 |
|---|---|---|
| 项目是什么 | README | PROJECT_STATE 不复制完整介绍 |
| AI 如何工作 | AGENTS + PROJECT_RULES | README 不列完整规则 |
| 文件在哪里 | PROJECT_INDEX | README 不列完整文件树 |
| 当前状态 | PROJECT_STATE | README 只显示摘要 |
| 任务生命周期 | TODO | PROJECT_STATE 不保存完整任务库 |
| 决策原因 | DECISION_LOG | TODO 只引用编号 |
| 用户可见变化 | CHANGELOG | Git Commit 不替代变更日志 |
| 版本完整内容 | releases | CHANGELOG 只写用户可见摘要 |
| 历史文件 | archive/README | PROJECT_INDEX 只保留入口和替代关系 |

## 6.1 冲突处理

发现两个正式文件内容冲突时：

1. 暂停依赖冲突信息的工作；
2. 根据正式来源表确定权威文件；
3. 检查 Git 和实际文件；
4. 修复错误文档；
5. 在 PROJECT_STATE 记录修复；
6. 大范围冲突建立整理任务。

# 7. 自适应项目结构

## 7.1 不存在唯一目录树

不同项目可能是：

- 单页网站；
- 全栈平台；
- Flutter App；
- Unity 游戏；
- AI 数据管线；
- 课程报告；
- 设计交付。

目录必须服务于实际项目，而不是模板展示。

## 7.2 目录决策顺序

### 第一：框架强制结构

例如：

- Next.js 的路由约定；
- Flutter 的 `lib/`、`android/`、`ios/`；
- Unity 的 `Assets/`、`Packages/`；
- Unreal 的 `Content/`、`Source/`；
- Python 包结构。

### 第二：现有合理结构

项目已可运行且结构基本清晰时，优先延续。

### 第三：独立单元

有多个独立构建或部署单元时，可以使用：

```text
apps/
├── web/
├── admin/
├── api/
└── worker/
```

只有一个应用时，不必增加 `apps/` 层。

### 第四：业务功能

应用内部可使用：

```text
features/
├── projects/
├── games/
└── skills/
```

后端可使用相同名称：

```text
modules/
├── projects/
├── games/
└── skills/
```

### 第五：真实共享

只有已经被多个应用使用的内容才抽取到共享包。

## 7.3 目录复杂度判断

创建新目录前回答：

1. 目录的稳定职责是什么？
2. 哪些文件会进入？
3. 当前是否已经有两个以上同类文件？
4. 是否存在长期增长预期？
5. 是否存在权限、部署或安全隔离？
6. 现有目录是否已足够？
7. 新目录是否会导致单文件多层路径？
8. 用户和 AI 是否会因此更快找到文件？

无法清楚回答时，不创建。

## 7.4 小、中、大项目

### 小型

```text
src/
public/
docs/
assets/
```

### 中型

```text
apps/
packages/
docs/
assets/
tests/
```

### 大型或多应用

可以增加更细层级，但每一层必须有明确职责。

## 7.5 禁止项

不得长期存在：

```text
misc/
other/
new/
latest/
final/
temp2/
杂项/
最终版2/
```

不得：

- 建立大量空目录；
- 为一个普通文件创建多层路径；
- 重复目录名称；
- 为未批准功能预留结构；
- 为了整齐大规模搬迁稳定项目。

# 9. 通用命名规则

## 9.1 文件和目录

除框架要求外：

- 小写英文；
- 英文短横线；
- 名称表达职责；
- 必要时加入日期、任务号、平台或版本；
- 避免无意义缩写。

示例：

```text
system-overview.md
homepage-mobile-v2.png
survey-cleaned-2026-08.csv
web-020-payment-test.md
```

## 9.2 当前有效版本

不能只依赖文件名中的 `final`。

当前有效版本必须通过：

- `PROJECT_INDEX.md`；
- Git；
- 任务或发布记录；

共同确认。

## 9.3 日期

需要日期时推荐：

```text
YYYY-MM-DD
```

例如：

```text
user-interviews-2026-08-01.md
```

## 9.4 任务和决议

```text
任务：WEB-020
决议：DR-WEB-20260801-001
```

# 12. AI 接手识别摘要

## 12.1 触发时机

AI 在以下场景中必须先输出识别摘要，再修改文件：

- 首次接手项目；
- 项目中断较长时间后恢复；
- 从其他 AI 接手写入权；
- 用户要求重新确认当前理解；
- 项目状态文件与实际内容可能存在偏差。

## 12.2 作用

识别摘要用于让用户快速检查：

- AI 是否找对项目；
- 当前任务是否正确；
- 是否遗漏阻塞或冻结规则；

# 13. TODO 与任务生命周期

## 13.1 状态

| 状态 | 说明 |
|---|---|
| 候选 | 尚未决定 |
| 已批准 | 用户决定执行 |
| 进行中 | 当前写入者实施 |
| 待验收 | 已实现并完成内部验证 |
| 已阻塞 | 等待条件 |
| 已完成 | 用户验收并完成发布/交付收尾 |
| 已取消 | 不再执行 |

## 13.2 用户验收

“已批准”和“已完成”都需要用户确认。

AI 可以：

- 建议批准；
- 判断已达到待验收；
- 提供验收证据；
- 在用户确认后执行收尾。

AI 不可以：

- 自行批准重大需求；
- 自行完成最终验收；
- 因测试通过直接标记已完成。

## 13.3 需求进入规则

### 明确且低风险的需求

用户明确要求执行、范围清楚且风险较低时：

- 建立任务；
- 状态进入“已批准”；
- 补充验收标准；
- 不需要先建立决议。

### 想法或远期设想

例如“以后是否可以增加社区功能”。

处理方式：

- 进入“候选”；
- 不立即开发；
- 不打断当前主要任务；
- 等用户确认价值、范围和优先级后再批准。

### 影响核心规则的需求

涉及以下内容时，先进入候选：

- 产品核心规则；
- 架构；
- 数据；
- 权限和安全；
- 收费；
- 部署平台；
- 高成本或不可逆方向。

完成影响分析和必要决议，并经用户确认后，才能进入“已批准”。

### 紧急故障

线上故障或关键交付阻断可以中断当前任务，但必须：

1. 建立独立紧急任务；
2. 记录被中断任务的当前状态和恢复点；
3. 使用独立修复分支（采用 Git 时）；
4. 修复完成后恢复原任务状态；
5. 不把紧急修复混入原任务的 Commit 或交付记录。

## 13.4 并行任务上限

个人项目默认：

```text
主要进行中任务：最多 1 个
紧急修复任务：最多 1 个
待验收任务：可以多个
候选任务：不限制
```

只有满足以下条件时才可偏离：

- 使用独立分支或独立项目副本；
- 文件边界明确；
- 不会覆盖同一状态文档；
- 用户明确同意。

# 14. Git、分支与 Commit

## 14.1 适用性

- 可部署代码项目：Git 必须使用。
- 无部署交付项目：强烈建议，但用户可以选择不使用。
- 混合项目：至少代码部分使用 Git。

## 14.1.1 远程仓库与 push 时机

- 每项目一个独立私有远程仓库（如 GitHub Private 仓库），仅作备份与版本管理；服务器不从远程仓库拉取代码（部署走本地 rsync 直推）。
- 本地 Commit 按任务正常进行；push 到远程仓库只与发布/交付绑定——用户确认部署上线（或正式交付）时随发布流程一并推送，开发期不要求每次提交都推送。
- 分支名中任务编号用小写（`task/web-012-payment`），Commit 中任务编号用大写（`feat(WEB-012): ...`），为有意约定。

## 14.2 分支

长期分支默认：

```text
main
```

任务分支：

```text
task/web-020-payment
```

紧急修复：

```text
hotfix/web-031-login-error
```

## 14.3 Commit

```text
feat(WEB-020): 增加套餐和订单结构
fix(WEB-021): 修复移动端标题换行
docs(WEB-022): 更新部署说明
chore(release): 发布 v0.2.0
```

## 14.4 Commit 粒度

合理拆分：

```text
feat(WEB-020): 增加套餐和订单数据库结构
feat(WEB-020): 增加创建支付订单接口
feat(WEB-020): 增加用户购买页面
test(WEB-020): 增加订单到账测试
docs(WEB-020): 更新支付说明
```

不得：

- 把全部工作塞进“完成支付功能”；
- 每修改一行就 Commit；
- 把不相关任务混在同一 Commit。

# 15. 版本、发布与交付

## 15.1 语义化版本

```text
v主版本.功能版本.修复版本
```

- Patch：修复和小体验优化；
- Minor：新增功能；
- Major：不兼容或重大使用方式变化。

## 15.2 CHANGELOG 语言

保留：

```text
Added
Changed
Fixed
Removed
Security
```

这些英文分类是为了兼容 Keep a Changelog 和常见自动化工具。

分类标题使用英文，具体内容使用中文。

如果项目完全不需要自动化或跨语言协作，也可以统一改为中文，但同一项目内必须保持一致。

## 15.3 可部署项目发布

发布前：

1. 任务达到待验收；
2. 用户确认可发布；
3. 测试和构建通过；
4. 数据迁移和安全检查；
5. 更新版本和 CHANGELOG；
6. 创建发布说明；
7. 合并 main；
8. push 到远程仓库（先入库备份）；
9. 部署；
10. 目标环境验收（线上验证）；
11. 创建 release commit（`chore(release): 发布 vX.Y.Z`）与 Git Tag，并 push Tag；
12. 用户最终确认；
13. 标记完成。

## 15.4 无部署项目交付

交付前：

1. 任务达到待验收；
2. 格式、文件名、页数或提交要求检查；
3. 生成最终文件；
4. 放入 `deliverables/` 或约定位置；
5. 提供交付清单；
6. 用户最终确认；
7. 更新状态和交付记录；
8. 采用 Git 时提交并可选建立 Tag；
9. 标记完成。

## 15.5 版本说明模板

- 日期：
- 项目模式：
- 版本：
- Git Tag：不适用 / v0.2.0
- 状态：

## 包含任务

## 新增

## 修改

## 修复

# 17. 多 AI 与人机协作

## 17.1 单一写入者原则

以下工作不能在同一项目副本中并行发生：

- 两个 AI 同时改代码；
- 一个 AI 重构目录，另一个 AI 新增功能；
- 一个 AI 修改文档，另一个 AI依据旧文档执行；
- 用户和 AI 同时改同一个文件但没有合并计划。

## 17.2 允许并行

可以并行：

- 一个 AI 执行，另一个 AI 审查；
- 一个 AI 研究，另一个 AI 在独立副本中试验；
- 多个 AI 分别给方案，由用户选择；
- 不同任务在独立分支和明确文件边界下进行。

并行任务的数量上限和偏离条件见第 13.4 节，本节不重复定义。

## 17.3 写入权切换

写入权切换清单：

```markdown
- 当前写入者停止修改：
- 当前分支：
- 未提交内容：
- PROJECT_STATE 已更新：
- 交接包已生成：
- 新写入者已确认：
```

## 17.4 用户验收

用户是默认且唯一最终验收人。

即使 AI：

- 自动测试通过；
- 构建通过；
- 自己检查无误；
- 另一个 AI 审查通过；

任务仍然只能进入“待验收”。

# 19. 更新与维护

## 19.1 “实时”的含义

不是每保存一次文件就更新文档。

是指相关事件发生后：

- 当前工作会话内；
- 不晚于 Commit；
- 不晚于任务切换；
- 不晚于暂停；
- 不晚于合并；
- 不晚于交接。

## 19.2 更新矩阵

| 事件 | 文件 |
|---|---|
| 新需求 | TODO |
| 任务开始、阻塞、恢复、待验收 | TODO + PROJECT_STATE |
| 当前主要任务或下一步变化 | PROJECT_STATE |
| 阶段变化 | PROJECT_STATE + README 摘要 |
| 重要文件变化 | PROJECT_INDEX |
| 重大决定 | DECISION_LOG |
| 用户可见变化 | CHANGELOG |
| 正式发布/交付 | 状态、TODO、发布/交付说明 |
| 归档 | PROJECT_INDEX + archive/README |
| 交接或中断 | PROJECT_STATE |
| 强制规则变化 | 精简执行版 + 参考版对应部分 |

## 19.3 不更新的情况

普通代码内部变化不更新索引。

每个小函数完成不更新状态。

普通 Bug 进度不更新 README。

纯内部重构不写用户 CHANGELOG。

# 20. 异常处理

## 20.1 上下文不足

AI 至少更新：

- 当前进度；
- 下一步；
- 未同步文档；
- 风险；
- 未提交文件。

## 20.2 工具失败

如果测试、构建、文件写入或 Git 工具失败：

- 不声称通过；
- 保留错误摘要；
- 记录复现步骤；
- 任务保持进行中或已阻塞；
- 写明恢复条件。

## 20.3 权限不足

缺少账号、部署权限或外部资源时：

- 任务改为已阻塞；
- 明确需要谁提供什么；
- 不用虚构结果代替验证。

# 22. 归档

归档判断发生在每次任务收尾（精简执行版第 7.3 节），不是等定期维护检查才处理。任务中一旦产生被替代的旧文件，应在该任务收尾时完成删除或归档。

## 22.1 应归档

- 被替代的需求；
- 历史设计；
- 旧数据；
- 旧演示稿；
- 需要追溯的历史方案。

## 22.2 不应归档

- 缓存；
- 构建产物；
- 可重新生成文件；
- 无价值临时文件；
- 敏感信息。

# 23. Token 优化

1. 先读入口和状态。
2. 按任务读取。
3. 普通代码按模块索引。
4. 非文本重要文件单独登记。
5. 默认跳过归档、依赖、构建、缓存和日志。
6. PROJECT_STATE 保持 150 至 200 行。
7. TODO 不保存全部历史。
8. 完整参考版只按章节读取。
9. 精简执行版负责日常约束。
10. 索引失效时先修复索引。

# 24. 项目健康检查

旧版“状态一致性检查”和“定期维护检查”合并为本章。

## 24.1 快速检查

触发：

- AI 接手；
- 恢复工作；
- 切换分支；
- 开始任务。

检查：

- TODO 和当前任务；
- 当前分支；
- 未提交修改；
- 索引关键路径；
- `SYNC_PENDING`；
- 当前写入者；
- 根目录是否存在不应长期保留或状态不明的文件。

## 24.2 完整检查

触发：

- 发布或交付前；
- 大型功能后；
- 长期中断后；
- 更换主要工具或 AI；
- 文件明显增多；
- 多个旧版本冲突。

检查：

- 根目录；
- README 与正式版本；
- CHANGELOG 与 Tag；
- 项目状态；
- TODO 长度；
- 索引有效性；
- 归档；
- 空目录；
- 单文件多层目录；
- 路径重复；
- 文档链接；
- 敏感数据；
- 常用文件定位效率。

大量问题建立独立整理任务。

## v1.4 Final — 2026-08-07

- 修正发布流程冲突：Git Tag 与 release commit 移至部署和线上验证之后，避免 Tag 指向未验证版本（原 §15.3 顺序与部署体系发布闭环冲突）；
- 明确远程仓库与 push 时机：每项目一个独立私有远程仓库，本地 Commit 照常，push 仅与发布/交付绑定；
- 精简版根目录白名单明确纳入部署必需文件（Dockerfile、docker-compose.yml、docker-entrypoint.sh 视为运行必需配置）；
- 明确编号大小写约定：分支名小写、Commit 编号大写；
- AGENTS.md 模板补充“完整参考版未随项目安装时须注明其位置”的要求；
- 更新矩阵“正式发布或交付”行补充远程 push 与 Git Tag。

## v1.3 Final — 2026-08-01

- 修复“规则存在但 AI 不自动执行”的系统性问题：将静态描述规则挂到工作流必经节点；
- 精简执行版第 7.3 节升级为完整任务收尾检查清单，新增文件归位、命名复核、根目录检查和被替代旧文件归档四项必查；
- 快速指令块新增任务收尾检查要求；
- 归档触发从定期维护检查前移到每次任务收尾；
- 接手快速检查（两份文件）新增根目录检查项；
- AGENTS.md 模板新增内联“每任务收尾检查”小节，避免 AI 必须重读规则文件才会执行收尾检查。

## v1.2 Final — 2026-08-01

- 恢复需求进入规则，区分明确需求、想法、核心规则变化和紧急故障；

- 将无部署项目的 Git 规则统一为 SHOULD，用户可明确选择无 Git 模式；
- 明确规范版本历史只在完整参考版维护；
- 将交接输出中的“已完成”改为“本轮完成内容”，避免与任务状态混淆；
- 收拢使用说明与参考版之间的规则边界；
- 修正第 14 至 24 章二级小节编号与所属章节不一致的问题；
- 在 PROJECT_STATE 核心内容清单中补充“当前进度（已完成与未完成）”；
- 消除多 AI 章节中对并行任务上限的重复定义，统一指向第 13.4 节。
